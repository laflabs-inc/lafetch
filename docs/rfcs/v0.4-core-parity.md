# v0.4 Core parity와 logical lifecycle RFC

상태: 구현 완료

## 목표

Reliability 기능을 확장하는 동안 일반적인 HTTP client 사용자가 별도 wrapper를 만들어야 하는 Core API 공백을 함께 제거합니다. 기능 수 자체를 경쟁 목표로 삼지 않고 다음 조건을 모두 만족하는 항목만 v0.4에 포함합니다.

- 반복되는 일반 HTTP client 사용 사례여야 합니다.
- 기존 Lafetch 문법으로 표현할 수 없거나 불필요한 wrapper가 필요해야 합니다.
- Browser, Node.js, Next.js와 Workers/Edge에서 같은 계약을 제공할 수 있어야 합니다.
- v0.5 Feature·Transport SDK와 v0.6 Observability 책임을 침범하지 않아야 합니다.
- Body ownership, Retry 안전성과 bundle 예산을 약화하지 않아야 합니다.

이번 단계에서 채택하는 공개 API는 logical lifecycle `.on(handler)`와 누락된 `options()` named method입니다.

## 단일 lifecycle API

event 이름별 overload 대신 하나의 `.on(handler)`만 제공합니다.

```ts
const api = lafetch
  .create({ baseUrl: "https://api.example.com" })
  .on(async (event) => {
    if (event.type === "request") {
      event.request = event.request.header(
        "Authorization",
        `Bearer ${await getToken()}`,
      );
    }

    if (event.type === "response") {
      console.log(event.response.status);
      console.log(event.response.meta.attempts);
    }
  });
```

```ts
type LLifecycleEvent =
  | {
      readonly type: "request";
      request: LRequest;
    }
  | {
      readonly type: "response";
      readonly response: LResponse;
    };

type LLifecycleHandler = (
  event: LLifecycleEvent,
) => void | Promise<void>;
```

`event.request`의 slot만 쓰기 가능한 이유는 `LRequest` 자체가 immutable builder이기 때문입니다. Header나 Timeout을 바꾸려면 새 `LRequest`를 만들어 event에 다시 연결합니다. native 객체를 직접 mutate하는 두 번째 문법은 제공하지 않습니다.

### 실행 의미

- `api.on(handler)`와 `request.on(handler)`를 지원합니다.
- client handler가 먼저, request handler가 나중에 실행됩니다.
- 같은 범위에서는 등록 순서를 유지합니다.
- `request`는 Transport attempt가 아니라 logical request 실행 전에 한 번 발생합니다.
- `response`는 Retry와 자동 decoding·validation이 끝나 `LResponse`가 만들어진 뒤 한 번 발생합니다.
- handler는 async를 지원하며 순서대로 기다립니다.
- request handler 실패는 Transport를 시작하지 않습니다.
- response handler 실패는 해당 `LResponse` 소비를 실패시킵니다.
- `mapError()`는 lifecycle handler 실패도 request 또는 response phase에서 처리할 수 있습니다.

### Retry와 Telemetry

`.on()`에는 `attempt`를 노출하지 않습니다.

- 최종 시도 수는 `event.response.meta.attempts`에서 확인합니다.
- attempt별 관찰은 기존 Telemetry의 `attempt:start`, `attempt:response`, `attempt:error`를 사용합니다.
- forced Retry, Response 교체와 attempt mutation은 v0.5 Feature·Transport SDK의 책임입니다.

logical lifecycle과 attempt lifecycle을 분리하여 인증 Header 갱신 같은 일반 기능이 내부 Retry 엔진에 종속되지 않게 합니다.

## `LRequest`와 `LResponse`를 사용하는 이유

`.on()`은 Lafetch의 공개 logical lifecycle입니다. 따라서 사용자가 구성한 요청과 최종 결과를 각각 `LRequest`와 `LResponse`로 연결합니다.

| 계층 | 타입 | 역할 |
| --- | --- | --- |
| Public logical lifecycle | `LRequest`, `LResponse` | 요청 구성과 최종 결과 |
| Telemetry | `RequestEvent` snapshot | Retry·Cache·Deduplication 관찰 |
| Feature·Transport | native `Request`, `Response` | 실제 attempt 제어 |

native `Request`와 `Response`를 공개 `.on()`에 사용하면 retry attempt hook처럼 보이고 기존 immutable builder 문법과 분리됩니다. 반대로 Feature hook까지 `LRequest`로 감싸면 Body ownership과 실제 전송 객체 제어가 불명확해집니다.

### 안전 경계

- lifecycle에 전달된 request draft는 설정 전용이며 직접 `await`할 수 없습니다.
- handler는 같은 logical request에서 파생된 `LRequest`만 다시 연결할 수 있습니다.
- 다른 client나 다른 URL에서 만든 `LRequest`로 교체해 client 격리 경계를 우회할 수 없습니다.
- request draft에 lifecycle handler를 다시 등록해 현재 dispatch를 재귀 호출할 수 없습니다.
- 설정 변경은 실행 전에 완료되며 Retry 모든 attempt에 동일하게 적용됩니다.

## Response terminal 경계

`response` event는 실제 `LResponse`가 생성되는 direct `await`, `then`, `catch`, `finally` 소비에서만 발생합니다.

- `as("json")`, `as("text")` 등 data terminal은 값을 직접 반환하므로 `LResponse`를 만들지 않습니다.
- `as("response")`는 native Buffered `Response` 소유권을 선택합니다.
- `as("stream")`은 Header 우선 live `LStreamResponse` 소유권을 선택합니다.

이 terminal들을 억지로 `LResponse`에 다시 포장하면 반환 계약, Streaming backpressure 또는 Body decoding 의미가 달라집니다. request event는 terminal과 무관하게 실행되지만, raw·data·stream terminal의 세부 관찰은 Telemetry와 v0.5 Feature API를 사용합니다.

## OPTIONS named method

기본 Retry safe method에는 이미 `OPTIONS`가 포함되어 있지만 `LClient`에는 named method가 없습니다. 사용자가 표준 HTTP method에 `request("OPTIONS", url)`을 사용해야 하는 비대칭을 제거합니다.

```ts
const response = await api.options("/capabilities");
```

`OPTIONS`는 Fetch에서 Body를 기술적으로 허용하지만, named method는 일반적인 capability·preflight 성격에 맞춰 bodyless request로 제공합니다. Body가 필요한 비표준 사용 사례는 명시적인 `request("OPTIONS", url)`을 사용합니다.

## 제외 범위

- `.from(Request)`
- Form/FormData convenience API
- Upload·Download progress
- error/finally lifecycle event
- request·response attempt 교체
- forced Retry
- React·Next.js 전용 API

Progress와 bounded `HttpStatusError` data는 v0.6, 고급 hook 제어는 v0.5에 유지합니다.

## 검증 계약

- client → request handler 순서와 등록 순서
- request·response event의 discriminated union narrowing
- Retry 전체에서 logical event가 한 번만 실행
- async handler와 handler 오류의 `mapError()` phase
- request draft 직접 실행, 다른 계보 교체와 재귀 `.on()` 차단
- direct `LResponse`와 explicit terminal 경계
- 같은 `LRequest`의 다중 direct 소비에서도 response event 한 번
- `OPTIONS` method와 bodyless Type-State
- Node.js, Chromium, Workers/Edge와 Next.js
- declaration, packed JavaScript·TypeScript consumer
