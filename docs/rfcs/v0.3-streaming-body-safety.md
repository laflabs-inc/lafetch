# RFC: Lafetch v0.3 Streaming과 본문 안전성

상태: 계약 확정, 구현 및 통합 CI 검증 완료 (`2026-07-26`)

대상 버전: `0.3.0-alpha`

기준 버전: `0.2.1-alpha.0`

## 결정 요약

v0.3은 기존 Buffered 실행 의미를 유지하면서 모든 명시적 응답 소비를 하나의 `as(mode)` terminal로 통합합니다.

```ts
const response = await api
  .get("/events")
  .timeout("2m")
  .as("stream");
```

```ts
interface RequestBuilder<TData> {
  as<TMode extends AvailableResponseMode>(
    mode: TMode,
  ): Promise<ResponseForMode<TData, TMode>>;
}
```

- 지원 mode는 `json`, `text`, `bytes`, `blob`, `formData`, `result`, `response`, `stream`으로 닫혀 있습니다.
- `as(mode)`는 literal과 유효한 union 변수를 모두 받고 mode에 맞는 반환 union을 추론합니다.
- `as("stream")`은 상태와 Header가 확정되면 실제 Fetch `Response`에 편의 API만 더한 `LafetchStreamResponse`를 반환합니다.
- `response.body`는 네트워크 본문과 연결된 단일 소비 `ReadableStream<Uint8Array> | null`입니다.
- `response.pipe()`와 반환 Stream의 `forEach()`는 nullable 처리와 반복 소비 boilerplate를 줄이지만 기존 Response·Web Stream API를 대체하지 않습니다.
- 직접 `await`와 `stream` 외 모든 mode는 Buffered 실행을 유지합니다.
- `result`는 자동 디코딩 데이터와 HTTP·실행 metadata를, `response`는 Buffered Fetch `Response`를 반환합니다.
- `as("response")`를 Streaming으로 변경하지 않습니다.
- 명시적 `bytes`와 자동 binary decoding은 `Uint8Array`를 반환합니다.
- Buffered 기본 상한은 기존 `16 MiB`를 유지합니다.
- Streaming은 기본적으로 전체 크기를 제한하지 않습니다.
- 사용자가 `maxResponseBytes(n)`을 명시한 Streaming만 실제 전달 Byte를 제한합니다.

## 배경

v0.2.1은 모든 응답을 제한된 크기로 읽은 뒤 보관하고, `asJson()`, `asRaw()` 같은 개별 terminal 이름을 사용했습니다. 같은 Builder를 여러 번 소비할 수 있고 Buffered `Response`도 독립적으로 반환하지만, 본문 전체가 도착하기 전에는 결과를 받을 수 없습니다.

SSE, AI token streaming, 대용량 다운로드에는 Header 수신 후 Body chunk를 즉시 전달하는 별도 실행 경로가 필요합니다. Buffered와 Streaming을 하나의 자동 동작으로 합치면 반환 시점, Retry, Timeout, Cache, 다중 소비 규칙이 응답 크기에 따라 달라지므로 두 계약을 명시적으로 분리합니다.

## 목표

- v0.2.1의 데이터 우선 문법과 Buffered 다중 소비를 유지합니다.
- 첫 Body chunk를 전체 응답 완료 전에 전달합니다.
- Streaming 경로에서 Lafetch가 전체 Body를 보관하지 않습니다.
- 실제 전달한 Byte를 기준으로 선택적 크기 상한을 적용합니다.
- Timeout과 Abort를 Body 종료까지 유지합니다.
- Body를 사용자에게 노출한 뒤에는 Retry하지 않습니다.
- Cache, Deduplication, Schema validation과의 충돌을 실행 전에 차단합니다.
- Browser, Node.js, Next.js, Workers/Edge에서 같은 Web Stream 계약을 제공합니다.

## 비목표

- v0.2.1 terminal 전체를 `.json()`, `.text()`, `.raw()` 형태로 다시 작성하지 않습니다.
- mode마다 별도 `asJson()`, `asStream()` 호환 alias를 유지하지 않습니다.
- 사용자 정의 문자열 decoder나 개방형 mode registry를 추가하지 않습니다.
- Node.js 전용 `Readable`을 공개 API로 추가하지 않습니다.
- SSE, NDJSON, JSON token parser를 코어에 포함하지 않습니다.
- Streaming Cache, multicast Deduplication, 업로드 진행률을 구현하지 않습니다.
- Protocol/Contract layer, Server adapter, OpenAPI, Mock framework를 추가하지 않습니다.
- 알파 내부 API를 위한 호환 alias나 Migration layer를 만들지 않습니다.

## 공개 API

### `as(mode)`

`as(mode)`는 실제 `Promise`를 반환하고 Builder 설정을 종료합니다. `stream` mode의 반환값은 실제 Fetch `Response` 인스턴스인 `LafetchStreamResponse`입니다.

```ts
const response = await api
  .get("/downloads/report.csv")
  .as("stream");

const reader = response.body?.getReader();

while (reader) {
  const { done, value } = await reader.read();
  if (done) break;
  consume(value);
}
```

간단한 소비는 편의 계층을 사용합니다.

```ts
const response = await api.get("/events").as("stream");
await response.pipe("text").forEach((chunk) => {
  consume(chunk);
});
```

`pipe()`는 byte Stream, `pipe("text")`는 text Stream, `pipe(transform)`은 표준 `ReadableWritablePair`의 출력 Stream을 반환합니다. 반환된 `LafetchReadableStream`은 native `ReadableStream`이며, `forEach()`만 추가로 제공합니다. callback은 순차적으로 `await`되고 실패하면 Stream을 취소합니다.

`status`, `statusText`, `headers`, `url`, `redirected`, `body`, `text()`, `clone()`과 `body.pipeThrough()`는 원본 Response 의미를 보존합니다. 사용자가 `clone()` 또는 `tee()`로 추가 buffering을 만들면 그 메모리와 backpressure는 사용자 책임입니다.

### 소비 방식 비교

| Terminal | 실행 | 반환 시점 | 다중 소비 | 기본 상한 |
| --- | --- | --- | --- | --- |
| 직접 `await` | Buffered | Body 완료 후 | 가능 | `16 MiB` |
| `as("json" | "text" | "bytes" | "blob" | "formData")` | Buffered | Body 완료 후 | 가능 | `16 MiB` |
| `as("result")` | Buffered | Body 완료 후 | 가능 | `16 MiB` |
| `as("response")` | Buffered | Body 완료 후 | 가능 | `16 MiB` |
| `as("stream")` | Streaming | Header 확정 후 | 불가 | 없음 |

`as("response")`는 Fetch `Response`를 반환하지만 이미 제한된 크기로 보관된 Body의 독립 복제본입니다. 실시간 Body가 필요할 때만 `as("stream")`을 사용합니다.

## Type-State와 실행 전 검증

`as("stream")`은 응답 소비 상태가 `open`인 Builder에만 노출합니다.

```ts
api.get("/events").as("stream");                  // 허용
api.get("/events").validate(schema).as("stream"); // TypeScript 오류
api.get("/events").cache("1m").as("stream");      // TypeScript 오류
api.get("/events").dedupe().as("stream");         // TypeScript 오류
```

JavaScript, `any`, 사용자 Feature를 통한 우회는 Transport 실행 전에 검증합니다.

- Response Schema가 있으면 `HttpConfigurationError`
- `cache` 또는 `dedupe` capability가 있으면 `HttpFeatureConflictError`
- Feature graph 자체가 잘못됐으면 기존 `HttpFeatureConflictError`

모든 조합을 Type-State로 표현하지 않습니다. 확실한 불변식만 IDE에서 제거하고, 동적 Feature 조합은 Runtime이 검증합니다.

## Builder 소비 소유권

같은 Builder 인스턴스는 Buffered 또는 Streaming 중 하나의 실행만 소유합니다.

- Buffered 소비는 기존처럼 같은 실행 결과를 여러 번 독립적으로 소비할 수 있습니다.
- 첫 `as("stream")` 호출이 Streaming 소유권을 얻습니다.
- 같은 Builder의 두 번째 `as("stream")`은 `HttpConsumptionError`로 실패합니다.
- Streaming 이후 직접 `await` 또는 다른 `as(mode)` 호출도 `HttpConsumptionError`로 실패합니다.
- Buffered 실행이 시작된 뒤 `as("stream")`을 호출해도 같은 오류로 실패합니다.
- 혼합 소비를 두 번째 네트워크 요청으로 암묵적으로 바꾸지 않습니다.

```ts
const request = api.get("/large-file");
const streaming = request.as("stream");

await request.as("response"); // HttpConsumptionError
```

같은 Streaming 결과를 여러 곳에서 기다려야 한다면 `as("stream")`을 한 번 호출해 반환된 Promise를 공유합니다. 두 개의 독립 요청이 필요하면 Builder를 두 번 생성합니다.

## 크기 상한

기존 `maxResponseBytes(bytes)`를 유지하며 새 단위 타입이나 별도 설정 메서드를 추가하지 않습니다.

```ts
const response = await api
  .get("/downloads/report.csv")
  .maxResponseBytes(1024 * 1024 * 1024)
  .as("stream");
```

- Buffered 실행은 설정이 없으면 기존 기본값 `16 MiB`를 적용합니다.
- Streaming 실행은 설정이 없으면 전체 크기를 제한하지 않습니다.
- Streaming에서 명시한 상한은 누적 전달 Byte에 적용합니다.
- `Content-Length`는 정확성이나 압축 상태를 보장하지 않으므로 상한 판정의 근거로 신뢰하지 않습니다.
- Header가 없거나 실제보다 작아도 각 chunk의 `byteLength`를 누적합니다.
- 상한을 넘기는 chunk는 사용자 Stream에 전달하지 않고 원본 Body를 취소합니다.
- 초과 시 기존 `HttpResponseTooLargeError`를 사용하며 Retry하지 않습니다.

상한은 전체 JavaScript heap이 아니라 Lafetch가 읽거나 전달한 Body payload Byte에 대한 계약입니다. Fetch 구현 내부 Buffer, 사용자 `clone()` 또는 `tee()`, decoder와 사용자 저장소의 메모리는 포함하지 않습니다.

## Status와 Retry

Retry는 accepted Response를 사용자에게 노출하기 전까지만 허용합니다.

1. Transport 또는 Feature interceptor가 Response를 반환합니다.
2. `afterResponse`와 `attempt:response`를 실행합니다.
3. Retry 대상 Status이면 Body를 취소하고 다음 시도를 시작합니다.
4. 최종 Status가 허용되면 Streaming Response를 반환합니다.
5. 이후 Body 오류, Timeout, Abort는 Stream을 실패시키고 Retry하지 않습니다.

일부 Body를 전달한 뒤 다른 응답으로 교체하면 중복 데이터나 파일 손상이 발생하므로 금지합니다.

최종 Status가 허용되지 않으면 Body를 사용자에게 노출하지 않고 취소한 뒤 `HttpStatusError`로 실패합니다. 오류의 `response`는 Status와 Header를 가진 body-less snapshot입니다. 오류 Body를 직접 처리할 사용자는 해당 Status를 `acceptStatus()`로 명시적으로 허용합니다.

## Timeout과 Abort

`timeout()`, `attemptTimeout()`, 사용자 `AbortSignal`은 Header 수신이 아니라 Body 종료 시점까지 적용합니다.

| 상황 | 결과 |
| --- | --- |
| 전체 Timeout | Body 읽기가 `HttpTimeoutError` (`scope: "total"`)로 실패 |
| 시도 Timeout | Body 읽기가 `HttpTimeoutError` (`scope: "attempt"`)로 실패, Retry 없음 |
| 사용자 Abort | Body 읽기가 `HttpAbortError`로 실패 |
| 소비자 `body.cancel(reason)` | 원본 Body 취소 후 lifecycle 정리 |

Timeout 또는 Abort 시 원본 reader를 취소하고 Timer와 Signal listener를 정리합니다. 사용자가 Body를 끝까지 읽지 않을 때는 `response.body?.cancel()`을 호출해야 합니다. Timeout도 없고 읽기나 취소도 하지 않으면 해당 네트워크와 Feature lifecycle은 열린 상태로 남을 수 있습니다.

## 오류 매핑

- `as("stream")` Promise가 완료되기 전 실패는 기존 `phase: "request"` Mapper 경로를 사용합니다.
- Response가 반환된 뒤 Body 읽기 실패는 `phase: "response"`로 `mapError()`를 적용하고 Stream을 실패시킵니다.
- Body 노출 뒤에는 이미 완료된 `as("stream")` Promise를 다시 거부하지 않습니다.
- Response 단계 Mapper에는 Status와 Header를 보존한 body-less snapshot을 전달합니다.
- 소비자 `cancel()`은 정리 완료를 기다리되, 취소 자체를 다시 오류로 바꾸지 않습니다. 원본 취소 또는 finalizer가 실패한 경우에만 `cancel()`이 실패합니다.

## Cache와 Deduplication

`cache()`와 `dedupe()`는 `as("stream")`과 함께 사용할 수 없습니다.

- Cache write는 완성된 Body를 소유해야 합니다.
- Streaming Cache에는 tee, backpressure, 부분 entry 정책이 필요합니다.
- Deduplication follower의 속도 차이는 무제한 Buffering을 만들 수 있습니다.
- 한 소비자의 취소가 다른 소비자에게 미치는 규칙도 별도 multicast 계약이 필요합니다.

v0.3은 이 문제를 자동 `Response.tee()`로 숨기지 않습니다. Streaming Cache와 multicast가 필요해지면 별도 RFC에서 다룹니다.

## Feature lifecycle

기존 Hook 순서를 유지하되 Streaming의 완료 시점만 Body 종료로 이동합니다.

- `prepare`, `beforeAttempt`, `intercept`, `afterResponse`는 `as("stream")` Promise 완료 전에 실행합니다.
- `attempt:response`는 Header 확정 시점에 발생합니다.
- `request:success`와 `finalize`는 Body 정상 종료 뒤 실행합니다.
- Body 오류, Timeout, Abort, 소비자 취소는 오류 또는 취소 결과로 finalization을 한 번만 실행합니다.
- Body가 없는 Response는 `as("stream")` 반환 전에 finalization을 완료합니다.
- Streaming finalizer에는 Status와 Header를 보존한 body-less Response snapshot을 제공합니다.
- finalizer 실패는 마지막 Body read 또는 `cancel()`에 반영합니다.
- Telemetry sink 실패는 기존처럼 HTTP와 Stream 결과를 바꾸지 않습니다.

사용자 Feature가 `afterResponse`에서 Body를 읽거나 clone하면 그 Feature가 Streaming과 메모리 사용의 책임을 집니다. 공식 Cache와 Deduplication은 사전에 거부합니다.

## Streaming 업로드

새 공개 API는 추가하지 않습니다.

```ts
await api.post("/upload").body(stream);
```

하나의 `ReadableStream` 요청 Body는 재사용할 수 없습니다. Retry가 필요하면 기존 `bodyFactory()`로 시도마다 새 Stream을 생성합니다.

```ts
await api
  .post("/upload")
  .bodyFactory(() => createUploadStream())
  .retry(1, { methods: ["POST"] });
```

v0.3에서는 큰 업로드가 전체 Buffer로 변환되지 않는지와 Retry 경계만 회귀 테스트로 고정합니다.

## 구현 순서

1. Builder terminal을 닫힌 `as(mode)` overload로 통합합니다.
2. Builder에 Buffered/Streaming 소비 claim과 `stream` Type-State를 추가합니다.
3. Executor의 공통 준비·Retry 경로를 유지하면서 Streaming 실행 모드를 분리합니다.
4. Body wrapper에 Byte 추적, Timeout, Abort, 단일 settlement를 구현합니다.
5. Feature finalization과 최종 Telemetry를 Body 종료에 연결합니다.
6. Cache, Deduplication, Schema 충돌을 타입과 Runtime 테스트로 고정합니다.
7. Node.js, Chromium, Workers/Edge, Next.js, tarball 소비와 번들 예산을 검증합니다.

## 테스트 계약

### API와 소유권

- 모든 mode와 union mode 변수의 반환 타입 및 `as("stream"): Promise<LafetchStreamResponse>` 타입
- `as<T>(mode)` 타입 단언 및 알 수 없는 mode 거부
- terminal 뒤 Builder 설정 불가
- `validate()`, `cache()`, `dedupe()` 뒤 `as("stream")` 타입 오류
- 반복 Streaming과 Buffered/Streaming 혼합 소비 오류

### Body

- 첫 chunk가 전체 Body 완료 전에 전달
- 정상 완료, source error, consumer cancel
- `pipe()`의 빈 Body 정규화, text chunk 경계, 표준 transform 상호운용
- 순차 `forEach()` backpressure와 callback 오류 시 취소
- 실제 chunk 기준 명시적 상한과 정확한 경계
- 잘못된 `Content-Length`에 영향받지 않음
- 전체 Body를 retained Response로 보관하지 않음

### 정책과 lifecycle

- Status Retry는 노출 전에 동작
- Body 노출 뒤 오류는 Retry하지 않음
- 전체 Timeout, 시도 Timeout, 사용자 Abort
- `mapError()`의 request/response phase
- finalizer와 최종 Telemetry가 Body 종료 뒤 정확히 한 번 실행
- Body 없는 Response의 즉시 finalization
- Cache, Deduplication, Schema의 실행 전 거부

### 런타임

- Node.js 20, 22, 24 Web Stream
- Chromium `ReadableStream`과 `TextDecoderStream`
- Next.js App Router 소비
- Workers/Edge 격리 환경
- 실제 npm tarball의 TypeScript와 JavaScript 소비
- 브라우저 공개 API `48 KiB / 16 KiB gzip` 회귀 예산

## 거부한 대안

### `.stream()`

현재 공식 terminal은 `as("json")`, `as("text")`, `as("response")`처럼 `as(mode)` 문법으로 통일돼 있습니다. Streaming 하나만 별도 동사형으로 추가하면 두 번째 terminal 문법이 생기므로 `as("stream")`을 사용합니다.

### 개별 `asJson()`, `asRaw()`, `asStream()` 유지

초기 v0.3 구현은 v0.2.1의 명명 규칙을 따라 `asStream()`을 추가했습니다. 구현 검토에서 mode마다 메서드가 늘어나 Builder 자동완성을 오염시키고, `result`, Buffered `response`, live `stream`의 관계를 한눈에 보기 어렵다는 문제가 확인됐습니다. 닫힌 literal overload와 JavaScript runtime 검증으로 오타 안전성과 Type-State를 유지할 수 있으므로 단일 `as(mode)`로 대체합니다. 아직 pre-release 단계이므로 호환 alias는 추가하지 않습니다.

### `as("response")`를 Streaming으로 변경

기존 Buffered 다중 소비와 메모리 상한 계약을 조용히 깨뜨리므로 별도 terminal을 사용합니다.

### Fetch Response를 대체하는 전용 wrapper

완료 Metadata를 별도 객체에 넣거나 Response 메서드를 다시 구현하는 wrapper는 Web Platform과 상호운용성이 떨어지므로 거부합니다. `LafetchStreamResponse`는 다른 객체로 감싸지 않고 실제 `Response`에 `pipe()`만 추가하는 구조적 subtype입니다. `pipe()`가 반환하는 값도 실제 `ReadableStream`에 `forEach()`만 추가하므로 저수준 API를 그대로 유지합니다.

### Streaming 기본 16 MiB 상한

Streaming은 전체 Body를 보관하지 않으므로 Buffered와 같은 기본 총량 제한이 필요하지 않습니다. 대용량 다운로드를 기본적으로 실패시키지 않고, 총량 제한이 필요한 요청만 `maxResponseBytes()`를 명시합니다.

## 확정된 결정

1. 공개 terminal은 닫힌 `as(mode)` 하나만 제공
2. `json`, `text`, `bytes`, `blob`, `formData`, `result`, `response`, `stream` 지원
3. `bytes`와 자동 binary decoding은 `Uint8Array`
4. `as("stream"): Promise<LafetchStreamResponse>`이며 실제 Fetch `Response` 호환
5. Buffered 기본 `16 MiB` 유지, Streaming 기본 무제한
6. 명시적 `maxResponseBytes()`를 Streaming 실제 전달 Byte에도 적용
7. 같은 Builder의 반복 Streaming 및 Buffered 혼합 소비를 `HttpConsumptionError`로 거부

현재 구현과 로컬·통합 CI 검증 결과는 [개발 로드맵](../roadmap.md)의 v0.3 검증 근거에 기록합니다.
