# Lafetch v0.4 HTTP freshness RFC

상태: 구현 완료

## 목적

`.cache(ttl)`은 application cache의 명시적 수명 정책입니다. 이 RFC는 그 TTL과 origin 또는 intermediary가 보낸 `Cache-Control: max-age`, `Age`가 충돌할 때 더 오래된 Response를 재사용하지 않도록 최소 freshness 계약을 고정합니다.

Lafetch는 범용 HTTP intermediary cache를 다시 구현하지 않습니다. 호출자가 지정한 TTL을 항상 최종 상한으로 유지하고, 이해하는 HTTP freshness 신호는 그 수명을 줄이는 방향으로만 사용합니다.

## Freshness 계산

유효한 단일 `max-age`가 있으면 남은 수명은 다음과 같습니다.

```text
remaining = min(configured TTL, max(0, max-age - Age))
```

- `max-age`와 `Age`는 RFC 9111의 non-negative integer seconds로 해석합니다.
- `Age`는 `max-age`가 있을 때만 차감합니다. `max-age`가 없으면 명시적인 Lafetch TTL을 사용합니다.
- list 형태의 `Age`는 첫 member만 사용하고 첫 member가 유효하지 않으면 Header를 무시합니다.
- 중복되거나 비정수인 `max-age`, 인수가 없는 `max-age`와 닫히지 않은 quoted 값은 즉시 stale로 처리합니다.
- 기존 사용자 호환성을 위해 수신된 `max-age="60"`은 허용하지만 Lafetch가 quoted form을 생성하지는 않습니다.
- 매우 큰 정수는 JavaScript number overflow가 음수나 새 freshness로 바뀌지 않게 처리합니다. `max-age`만 넘치면 configured TTL이 상한이고, `Age`가 수명을 따라잡거나 함께 넘치면 보수적으로 stale입니다.
- `no-cache`, `no-store`, `private`가 함께 있으면 `max-age`보다 제한적인 directive를 우선합니다.

## 절대 만료 시각

Response가 Cache의 `afterResponse` 경계에 도착한 시각에 절대 만료 시각의 기준을 고정합니다. 이후 Body buffering, 다른 response hook 또는 Store commit queue를 기다리는 시간은 freshness를 연장하지 않습니다.

Cache commit 차례가 왔을 때 이미 만료됐다면 `Response.clone()`과 `CacheStore.set()`을 모두 생략합니다. 이 결정은 invalidation queue에서 확정한 absolute `expiresAt` 계약과 동일합니다.

## Revalidation

`304 Not Modified`는 stale Body와 갱신된 Header를 결합한 뒤 같은 freshness 계산을 다시 적용합니다.

- 304가 새 `Age`를 제공하면 그 값을 사용합니다.
- 304가 `Age`를 제공하지 않으면 이전 hop에서 받은 stale `Age`를 상속하지 않습니다. 성공한 validation 시점부터 새 freshness를 계산합니다.
- full response 또는 결합된 304가 Status, `Set-Cookie`, `Vary`, `no-cache`, `no-store`, `private` 때문에 저장 불가가 되면 기존 stale validator를 같은 Store+key generation queue에서 삭제합니다.
- `max-age=0` 또는 invalid freshness는 저장 write를 만들지 않지만, validator가 있는 기존 stale entry는 다음 명시적 revalidation에 사용할 수 있습니다.

Store 삭제 실패는 기존 `storeFailure: "throw" | "bypass"` 계약을 그대로 따릅니다. 오래된 generation의 cleanup이 더 새로운 invalidation 결과를 삭제하지 않도록 직접 `delete()`하지 않고 commit queue를 사용합니다.

## 의도적인 제외

- `Expires`와 `Date` 기반 heuristic freshness
- shared-cache 전용 `s-maxage`
- request `Cache-Control` directive 해석
- cache hit마다 동적으로 증가하는 `Age` Header 합성
- `stale-while-revalidate`, `stale-if-error`와 background task

외부 `CacheStore`가 private인지 shared인지 Core가 판정할 수 없고, `CacheEntry`에는 protocol intermediary가 필요한 stored-at·initial-age metadata가 없습니다. 이 정보를 불완전하게 추정하거나 Store 공개 계약을 확대하는 대신, 현재는 필수 TTL과 제한적인 response directive만 지원합니다.

## Bundle 결정

Freshness parser와 revalidation cleanup을 포함한 측정값은 다음과 같습니다.

- complete root: `54,114 / 16,590 bytes gzip`
- 대표 JSON 요청 초기 graph: `45,051 / 14,230 bytes gzip`
- Cache static closure: `5,100 / 2,278 bytes gzip`

대표 요청 `44/14 KiB`, Cache `5/2.5 KiB`와 complete root gzip `17 KiB` 상한은 유지합니다. Complete root minified만 실제 정확성 비용 218 bytes를 반영해 `52.75 → 53 KiB`로 조정합니다. HTTP 의미를 약화하거나 parser를 과도하게 축약해 이전 수치에 맞추는 선택은 하지 않습니다.
