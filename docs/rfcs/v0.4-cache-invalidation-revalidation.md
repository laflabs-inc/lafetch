# Lafetch v0.4 Cache invalidation·revalidation RFC

상태: 구현 완료

## 목적

외부 `CacheStore` 계약 위에서 stale Response를 안전하게 갱신하고, 동일한 application-cache key를 origin 결과로 교체하는 최소 공개 계약을 정의합니다. 별도 controller나 tag API를 만들지 않고 기존 `.cache()` 정책 안에서만 표현합니다.

## 공개 계약

```ts
await api.get("/catalog").cache("5m", {
  store,
  mode: "invalidate",
});

await api.get("/catalog").cache("5m", {
  store,
  mode: "revalidate",
});
```

- `mode: "invalidate"`는 최종 `Request`에서 계산된 key를 `delete()`한 후 origin으로 전송합니다. 성공하고 cacheable한 응답은 같은 key에 다시 저장됩니다.
- `mode: "revalidate"`는 만료 entry에 `ETag` 또는 `Last-Modified`가 있을 때 각각 `If-None-Match`, `If-Modified-Since`를 추가합니다.
- origin의 `304 Not Modified`는 저장된 status·Body와 새 응답 Header를 결합한 정상 Response로 교체합니다. `Content-Length`는 stale Body와 불일치할 수 있어 304 값으로 덮어쓰지 않습니다.
- validator가 없는 만료 entry는 삭제하고 일반 cache miss로 처리합니다.
- 기본 `mode: "default"`는 기존 요청의 read·expiry 동작을 바꾸지 않습니다.

두 동작을 별도 `.invalidateCache()`·`.revalidate()` 메서드로 만들지 않은 이유는 key·Store·TTL·민감 요청 우회 규칙을 다시 입력하는 중복 API와 계층 불일치를 피하기 위해서입니다.

`mode` 선언 때문에 일반 요청 graph가 커지지 않도록 기존 `44/14 KiB` 상한을 유지합니다. Cache module의 minified 예산은 실제 invalidation 분기 비용을 반영해 `4 KiB`에서 `4.75 KiB`로 제한적으로 조정하되 gzip 상한 `2.5 KiB`와 complete root `52/17 KiB`는 유지합니다. validator 처리와 304 결합은 stale 경로에서만 읽는 별도 dynamic chunk입니다.

## Body ownership과 Retry

Store의 stale Response는 읽기마다 독립 clone이어야 합니다. 304 결합은 해당 logical request가 소유한 clone의 Body만 사용하며 Store 원본이나 다른 요청의 Body를 소비하지 않습니다.

조건부 Header는 Cache `intercept` 시점의 실제 attempt `Request`에 적용합니다. Retry가 새 attempt를 만들면 Store를 다시 읽고 validator를 다시 적용하므로 attempt 간 `Request` 객체를 공유하지 않습니다. 304를 저장된 representation으로 교체한 뒤에만 status 판정과 decode가 진행됩니다.

## 실패 의미

기존 `storeFailure` 계약을 그대로 사용합니다.

- `"throw"`: invalidation `delete()`와 stale read 실패를 Cache Feature 오류로 노출합니다.
- `"bypass"`: Store 실패를 cache miss로 처리하고 origin 요청을 계속합니다.
- Transport, status, decode와 validation 오류는 Cache 정책이 삼키지 않습니다.

민감 Header·query·credentials가 감지된 요청은 기존과 같이 Cache 전체를 우회하므로 invalidation이나 revalidation도 수행하지 않습니다.

## 의도적인 제외

- tag·prefix·전체 Store invalidation
- stale-while-revalidate와 background task
- stale-if-error
- shared-cache directive 전체 구현
- framework Cache 또는 CDN revalidation

이 기능들은 다중 key 열거, task ownership 또는 platform adapter 계약이 필요하므로 현재 Core 단계에서 선행 도입하지 않습니다.
