# Lafetch v0.4 Retry 결정 RFC

상태: server-directed delay 계약 구현 완료, custom decision 계약 설계 중

## 목적

v0.4의 Retry는 재시도 횟수를 늘리는 기능이 아니라 다음 세 주체의 결정을 충돌 없이 합성해야 합니다.

1. Lafetch가 제공하는 method·status·network 기본 gate
2. 서버가 `Retry-After`로 전달하는 최소 대기 신호
3. 향후 사용자가 제공할 custom predicate

이 문서는 먼저 server-directed delay의 계약을 고정합니다. custom predicate와 forced Retry는 같은 안전 경계를 재사용할 수 있을 때만 후속으로 추가합니다.

## 확정 계약

### 표준 신호

Lafetch는 [RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)의 `Retry-After`만 자동 해석합니다.

- 정수 delay-seconds
- HTTP-date

잘못된 값은 오류로 만들지 않고 일반 Backoff로 돌아갑니다. `respectRetryAfter: false`이면 Header를 읽지 않습니다.

### 독립된 상한

`backoff.max`는 client가 계산한 fixed 또는 exponential delay의 상한입니다. 서버가 지정한 대기를 같은 값으로 자르면 서로 다른 정책이 조용히 결합됩니다.

따라서 `maxRetryAfter`를 별도 옵션으로 사용합니다.

```ts
await api.get("/jobs/1").retry(2, {
  maxRetryAfter: "1m",
  backoff: {
    type: "exponential",
    base: "200ms",
    max: "10s",
  },
});
```

- 기본 `maxRetryAfter`: 1분
- Header delay가 상한 이내: 해당 시간만큼 대기
- Header delay가 상한 초과: 상한으로 잘라 더 일찍 재시도하지 않고 현재 응답을 최종 실패로 처리
- total Timeout 또는 사용자 Abort: 대기 중에도 즉시 종료

상한 초과를 clamp하지 않는 이유는 서버가 제안한 시간보다 일찍 요청을 반복하면 overload나 rate limit을 악화시킬 수 있기 때문입니다.

### RateLimit과 비표준 Header

[RateLimit Header Fields for HTTP](https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/)는 현재 active Internet-Draft입니다. `RateLimit`, `RateLimit-Policy`, `X-RateLimit-*`는 core의 자동 Retry 신호로 해석하지 않습니다.

이 Header는 단일 실패 응답의 재시도 지연뿐 아니라 quota shaping을 표현하므로, 안정된 표준과 실제 수요 없이 `Retry-After`처럼 취급하면 의미가 달라질 수 있습니다.

## 안전 불변식

- Retry는 사용자가 `retry(count)`를 선언한 요청에서만 활성화됩니다.
- 기본 method gate는 `GET`, `HEAD`, `OPTIONS`입니다.
- unsafe method는 명시적 method 허용 또는 Idempotency policy 없이 자동 재시도하지 않습니다.
- accepted Streaming Body를 노출한 뒤에는 교체 Response를 만들지 않습니다.
- `bodyFactory()`가 없는 non-replayable Body는 전송 전에 거부합니다.
- server delay는 total Timeout과 사용자 Abort를 우회하지 않습니다.

## 검증 행렬

| 상황 | 결과 |
| --- | --- |
| delay-seconds가 상한 이내 | Header delay 사용 |
| HTTP-date가 상한 이내 | runtime clock 기준 delay 사용 |
| Header delay가 `backoff.max`보다 큼 | `maxRetryAfter` 이내면 Header delay 사용 |
| Header delay가 `maxRetryAfter`보다 큼 | 재시도하지 않음 |
| 잘못된 Header | 일반 Backoff 사용 |
| `respectRetryAfter: false` | 일반 Backoff 사용 |
| server delay 중 total Timeout·Abort | 즉시 종료 |

## 후속 결정

custom predicate와 forced Retry는 아직 공개 API로 확정하지 않습니다. 후속 설계는 다음 조건을 충족해야 합니다.

- method·idempotency gate를 predicate보다 먼저 적용
- status, normalized error와 attempt 문맥만 제공하고 raw Body의 중복 소비를 만들지 않음
- predicate throw를 Transport failure로 오분류하지 않음
- predicate가 total Timeout, 사용자 Abort와 Streaming ownership을 우회하지 못함
- 기본 정책을 강제로 뒤집는 기능은 이름과 비용이 명시적이어야 함

CacheStore, revalidation과 Deduplication 경쟁 상태는 이 RFC와 분리된 v0.4 작업으로 진행합니다.
