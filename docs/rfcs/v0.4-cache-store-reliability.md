# Lafetch v0.4 CacheStore 신뢰성 RFC

상태: 구현 완료

## 목적

외부 `CacheStore`는 network service, runtime storage 또는 사용자 adapter일 수 있습니다. Core가 Store 구현을 신뢰하거나 장애 의미를 암묵적으로 정하면 다음 문제가 생깁니다.

- 같은 entry의 `Response` Body가 여러 요청 사이에서 공유될 수 있음
- 만료 entry나 잘못된 entry가 정상 Cache hit처럼 사용될 수 있음
- Store 장애가 origin 요청을 막거나 반대로 조용히 origin 부하를 키울 수 있음
- `delete()`가 없는 Store 때문에 후속 invalidation 계약을 일반화할 수 없음

이 RFC는 revalidation 방식보다 먼저 Store의 최소 계약, 실패 의미와 공통 conformance suite를 고정합니다.

## CacheStore 계약

```ts
interface CacheStore {
  get(key: string): CacheEntry | undefined | Promise<CacheEntry | undefined>;
  set(key: string, entry: CacheEntry): void | Promise<void>;
  delete(key: string): void | Promise<void>;
}
```

- `get()`은 저장된 entry 또는 `undefined`를 반환합니다. Store는 만료 entry를 eviction하거나 원래 만료 시각과 함께 반환할 수 있습니다.
- `set()`은 전달된 `Response`를 snapshot합니다. 호출자가 원본 Body를 소비해도 저장된 entry가 변하지 않아야 합니다.
- 각 `get()` 결과는 다른 읽기와 독립된 `Response`, Header view와 Body를 제공해야 합니다.
- 같은 key를 다시 `set()`하면 이전 entry를 원자적으로 대체한 것처럼 관찰되어야 합니다.
- `delete()`는 필수이며 없는 key를 삭제해도 성공해야 합니다.
- `expiresAt`은 유한한 absolute epoch milliseconds입니다.
- Backend TTL 정밀도 때문에 만료 시각을 앞당길 수는 있지만 전달된 `expiresAt`보다 연장해서는 안 됩니다.

Core도 adapter 경계에서 `Response`와 `expiresAt`을 검증하고 만료를 다시 확인합니다. Store 자체 검증을 대체하기 위한 것이 아니라 clock race와 잘못된 외부 값을 Cache hit로 사용하지 않기 위한 방어입니다. 현행 Core는 만료 entry를 miss로 처리하고 삭제하지만 Store 계약 자체는 stale entry 반환을 금지하지 않습니다. 다음 revalidation 설계가 stale validator를 사용할 가능성을 미리 차단하지 않기 위해서입니다.

## Store 실패 정책

```ts
await api
  .get("/catalog")
  .cache("5m", {
    store,
    storeFailure: "throw",
  });
```

`storeFailure`는 closed string이며 `"throw"`와 `"bypass"`만 허용합니다.

### `throw`

기본값입니다.

- `get()`·만료 `delete()` 실패 또는 잘못된 entry는 `HttpFeatureError`의 `intercept` 실패가 됩니다.
- `set()` 실패는 `HttpFeatureError`의 `finalize` 실패가 됩니다.
- Cache와 Deduplication을 함께 사용하면 Cache commit 실패를 leader와 follower가 일관되게 관찰합니다.

Store 장애를 기본적으로 노출하는 이유는 조용한 fail-open이 장애를 숨기고 동시 요청을 origin으로 몰아 stampede를 만들 수 있기 때문입니다.

### `bypass`

Cache가 가용성 최적화일 뿐 요청 성공 조건이 아닌 서비스에서 명시적으로 선택합니다.

```ts
await api
  .get("/catalog")
  .cache("5m", {
    store,
    storeFailure: "bypass",
  });
```

- 읽기·만료 정리 실패 또는 잘못된 entry는 Cache miss로 처리합니다.
- 쓰기 실패는 origin Response를 바꾸지 않습니다.
- key callback, Transport, HTTP status, decoding과 validation 오류에는 영향을 주지 않습니다.

`bypass`는 Store 오류를 Lafetch 결과에서 제거하므로 adapter나 외부 Store client가 자체 logging과 metrics를 제공해야 합니다. Core-level Cache event는 v0.6 Observability 계약에서 별도로 다룹니다.

## Conformance suite

`@laflabs/lafetch/testing`의 `runCacheStoreConformance()`은 특정 test framework에 의존하지 않고 다음을 검사합니다.

1. Response metadata·Body와 `expiresAt` round trip
2. `set()` input Response와 저장 값의 write isolation
3. 반복 `get()`의 Body·Header read isolation
4. key isolation과 overwrite
5. expired entry를 반환할 때 만료 시각을 연장하지 않음
6. concurrent read isolation
7. idempotent delete

각 검사는 factory를 독립 호출하고 run별 namespace key와 best-effort cleanup을 사용합니다. 전체 runner는 adapter 오류 때문에 reject하지 않으며, 호출자는 `passed`와 `error`를 사용하는 test framework assertion으로 변환합니다.

## 제외

- Cache invalidation public API와 conditional revalidation
- stale-while-revalidate와 stale-if-error
- tag 또는 prefix invalidation
- Cache Store 장애 Telemetry event
- distributed lock과 cross-process request Deduplication

이 항목들은 이번 Store 계약을 기반으로 별도 v0.4 또는 v0.6 RFC에서 결정합니다.
